# Implemented website QA — 24–25 November 2026

## Result and scope

The currently implemented local journeys passed the checks below: the public illustrative homepage, account registration and verification, password login/recovery, My Weddings, wedding creation and private summary, and recoverable deletion/restoration. This is not a production release sign-off. Events, tasks, finance, invitations, RSVP, publishing and galleries remain sample UI or future backend work as recorded in [PROJECT_STATUS.md](PROJECT_STATUS.md).

Testing used fresh synthetic accounts, the actual local Next.js application and its configured Atlas database. No existing user wedding was deleted. The primary synthetic account is `qa-customer-20261124@example.test`; a second account, `qa-outsider-20261124@example.test`, exercised account isolation. Passwords, codes, cookies and database credentials are deliberately omitted from this report.

## Access protection and database verification

Live HTTP checks returned 401 for anonymous account/wedding/detail access; 404 for another verified account's detail/delete/restore attempts; 403 for an invalid-origin delete; 422 for an injected identity or incorrect confirmation; and 409 when attempting to reuse the retained slug. These tests used only synthetic fixtures.

The opt-in Atlas integration test passed for transactional initialization, concurrent slug uniqueness, owner/outsider isolation, delete, blocked reads after deletion, recovery listing, restoration and audit persistence. Its uniquely named internal fixtures were cleaned up by the test. Automated lifecycle tests also covered Manager denial, multi-owner deletion prevention and rollback when the audit write fails.

The persistent browser fixture's audit sequence was read from Atlas: `wedding.created`, `wedding.deleted`, `wedding.restored`, `wedding.deleted`. Its deletion marker remained present. Two synthetic browser/API accounts and that recoverable deleted wedding remain for traceability.

## Compass, network and logs

Compass originally had only a `localhost:27017` connection. **Make My Marriage — site database** now connects to the site's configured Atlas cluster and exposes `make_my_marriage_dev`. Its database overview was opened and refreshed.

During the resumed test, the user confirmed changing networks. Atlas explicitly reported that the current IP was not allowed. After the user requested that the agent perform the change, only Atlas's current single-address `/32` rule was added. Atlas reported Active and a fresh encrypted database connection and ping passed. Existing entries were preserved; TLS verification remained enabled. Future network/public-IP changes may require another scoped access-list update.

Atlas contained 40 request-log records at the final direct database inspection, covering all seven implemented route families. The stored fields were `_id`, `requestId`, `route`, `method`, `status`, `durationMs` and `occurredAt`; the TTL index was verified as 2,592,000 seconds (30 days). Audit history is retained separately. These are safe server request metadata and lifecycle events, not raw credentials, bodies, URLs or browser keystrokes. See [WEDDING_LIFECYCLE.md](WEDDING_LIFECYCLE.md).

## Fresh manual readiness pass — 25 November 2026

**Verdict: not ready to mark the whole customer journey working. This QA pass did not initiate commit or push.** The wedding functionality passed the tested scenarios, but normal signup and password recovery remain blocked for recipients outside the configured Resend test sender's permitted inbox. This pass used the normal saved environment; no temporary email capture or authentication bypass was enabled.

### Confirmed blocker

1. Registered a fresh synthetic customer through the browser using `qa-manual-normal-20261125@example.test`.
2. The UI displayed the check-email verification notice, while the running server recorded `Verification email delivery failed`.
3. Signing in with that account's correct password returned the verify-email notice; the customer could not proceed.
4. Requested a reset code for the existing verified synthetic account. The form advanced to code entry, but the server recorded `Could not send a password reset email`.

The configuration diagnostic independently confirmed the existing Resend restricted test sender. These are two affected journeys with the same delivery dependency. A verified sender and delivery to an independent test inbox must be checked before marking general-customer onboarding and recovery complete. Earlier local synthetic-inbox tests remain valid for application behavior, not external delivery.

### Fresh browser coverage

- Three public sample tabs and all five FAQ controls were exercised.
- Registration required fields, malformed email, country code, alphabetic phone input, phone spacing, password visibility and duplicate unverified-account feedback behaved as expected.
- Unverified-account login was blocked; a wrong password was rejected; uppercase email login for the verified test customer succeeded.
- Whitespace-only couple names were rejected. Unicode and HTML-like names rendered literally rather than becoming markup.
- A date below the UI minimum was invalid. A daylight-saving transition date in `America/New_York` retained the selected calendar day. Invalid timezone and slug feedback appeared; surrounding whitespace in a valid timezone worked.
- Location, title and description were left blank through creation successfully. Review/edit retained values. A reserved deleted address produced conflict feedback without losing inputs; selecting a new address allowed saving.
- Refresh retained saved details. The workspace showed no horizontal overflow at 320px, 390px or 1280px.
- Wrong-case confirmation kept deletion disabled; Cancel preserved access. Confirmed deletion and restoration worked, and restoration returned to the same workspace. Signed-out direct workspace access redirected to login.
- Recovery rejected an incomplete code and supported switching the email address. Valid-code completion in normal email mode was blocked by delivery; the earlier isolated reset test is recorded separately above.
- The existing Google account completed the account chooser, existing-access confirmation and callback into My Weddings. The Google-backed session was then signed out. No wedding belonging to the real Google account was changed.

25 explicit browser assertions were recorded as passing, alongside the additional observed validation and delivery cases above. The browser viewport was reset and the test sessions were signed out.
