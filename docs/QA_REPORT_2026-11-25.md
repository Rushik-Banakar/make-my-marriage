# Implemented website QA — 24–25 November 2026

## Result and scope

The currently implemented local journeys passed the checks below: the public illustrative homepage, account registration and verification, password login/recovery, My Weddings, wedding creation and private summary, and recoverable deletion/restoration. This is not a production release sign-off. Events, tasks, finance, invitations, RSVP, publishing and galleries remain sample UI or future backend work as recorded in [PROJECT_STATUS.md](PROJECT_STATUS.md).

Testing used fresh synthetic accounts, the actual local Next.js application and its configured Atlas database. No existing user wedding was deleted. The primary synthetic account is `qa-customer-20261124@example.test`; a second account, `qa-outsider-20261124@example.test`, exercised account isolation. Passwords, codes, cookies and database credentials are deliberately omitted from this report.

## Access protection and database verification

Live HTTP checks returned 401 for anonymous account/wedding/detail access; 404 for another verified account's detail/delete/restore attempts; 403 for an invalid-origin delete; 422 for an injected identity or incorrect confirmation; and 409 when attempting to reuse the retained slug. These tests used only synthetic fixtures.

The opt-in Atlas integration test passed for transactional initialization, concurrent slug uniqueness, owner/outsider isolation, delete, blocked reads after deletion, recovery listing, restoration and audit persistence. Its uniquely named internal fixtures were cleaned up by the test. Automated lifecycle tests also covered Manager denial, multi-owner deletion prevention and rollback when the audit write fails.

The persistent browser fixture's audit sequence was read from Atlas: `wedding.created`, `wedding.deleted`, `wedding.restored`, `wedding.deleted`. Its deletion marker remained present. Two synthetic browser/API accounts and that recoverable deleted wedding remain for traceability.

## Compass, network and logs

Compass originally had only a `localhost:27017` connection. **Make My Marriage — site database** now connects to the site's configured Atlas cluster and exposes `make_my_marriage_dev`. Its database overview was opened and refreshed.

During the resumed test, the user confirmed changing networks. Atlas explicitly reported that the current IP was not allowed. After the user requested that the agent perform the change, only Atlas's current single-address `/32` rule was added. Atlas reported Active and a fresh encrypted database connection and ping passed. Existing entries were preserved; TLS verification remained enabled. Future network/public-IP changes may require another scoped access-list update.

Atlas contained 40 request-log records at the final direct database inspection, covering all seven implemented route families. The stored fields were `_id`, `requestId`, `route`, `method`, `status`, `durationMs` and `occurredAt`; the TTL index was verified as 2,592,000 seconds (30 days). Audit history is retained separately. These are safe server request metadata and lifecycle events, not raw credentials, bodies, URLs or browser keystrokes. See [WEDDING_LIFECYCLE.md](WEDDING_LIFECYCLE.md).
